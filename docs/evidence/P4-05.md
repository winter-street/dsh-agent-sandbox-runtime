## Actual Harness/budget composition and durable continuation

`tests/adapters/serial-harness.test.ts` adds one complete composition scenario using actual Cordis, Harness LlmRuntime/AgentLoop/session lineage, the locally built original budget plugin, `createRuntimeHarnessIntegration` with its installed policy/tool plugin, `createRolePort`, `SerialWorkflow`, SQLite and the real artifact store. The original budget plugin must be built at `.sources/budget` as described in P3-05. The controlled provider yields fixed JSON and synthetic usage; `FakeSandbox` supplies a known artifact. This test does not claim to execute the generated Python.

The test creates an actual root agent and separate Planner/Executor/Reviewer child sessions. A real MCP stdio child process supplies a ranking reference through the durable registry and tool rules; the trusted host places that source-linked result in required tool-layer context. This is host retrieval, not a free-form model-driven MCP loop. An initial long history triggers one metered summary in the root session's existing work allocation. Planner and Executor then complete and `ApprovedCodeExecutor` automatically pauses before Python dispatch. After one approval, the bounded retry executor commits the controlled result; a deliberate exception occurs before Reviewer dispatch.

The test disposes the entire Harness context, closes SQLite, reconstructs Harness and its agent tree, reloads the budget plugin from its original ledger directory and reopens the original runtime database. The same serial workflow then reuses the stored planner/executor responses and execution result and dispatches only the reviewer. Independent runtime acceptance reads the committed `result.json` bytes and checks `verified=true` before success. The controlled sandbox records exactly one execute, and the committed artifact identity/checksum remains unchanged.

Observed assertions:

- Exactly four provider calls in order: root summary, planner, executor, reviewer; exactly four original-ledger reserves and four settlements, all in the original root scope. Synthetic usage is 4 × (20 input + 2 cache-read + 8 output) = 120; reserved=0 and unknown=0. Before interruption, usage was 90.
- Each of three durable `workflow.role_completed` events retains its deterministic workflow call ID and the original budget hook's separate modelCallId. Its receipt matches that reservation's settlement and session. None adopts the summary's settlement receipt.
- The shared context retains one summary coverage; the hostile-looking historical summary remains in recall messages and never enters system instructions. All dispatched role DTOs fit the configured 2400-token controlled estimate including output/safety allowances.
- The installed model policy records all four actual stream-dispatch decisions, demonstrating the composition plugin was active. Reinvoking the completed workflow adds no provider or sandbox call.
- One MCP call is committed, one approval is consumed, and each tool has one durable policy admission. Reference output remains in role messages, never system instructions; the original approval, tool result and execution are reused across reopening.
