# N05 保留集评测记录

## 首批串行与失败归因

`.runtime/n05-serial-20261119-0315/records.jsonl` 记录了首批 9 个真实 DeepSeek／OpenSandbox 槽位。用时 264.953 秒。三种策略都正确交付了缺列错误 `e23`。`e21`、`e22` 的六个槽位均生成统计、报告和 SVG，且图表通过独立验证。每个槽位都有用量回执。

对照独立参考与每个槽位最后提交的报告，六个产物中的 `time_bands` 都将计数写成了包含 `total` 和审核状态计数的对象。`e21 / tiered-finalize` 和 `e22 / tiered` 的 `severity` 也采用了这种嵌套结构。各组的总计正确，报告中相应 JSON 行继承了同一结构错误。严格比较因此同时判定统计和报告失败。原提示列出了键和统计含义，但没有逐项指定值类型。

`TASK-N05-v2.md` 明确两个字段是以整数为值的对象，并要求报告序列化同一份统计字段。`suite-n05-v2.json` 的指纹为 `eb1e6fb73bef7f7f48876ef6b33091567f99daa9f101b17fe0a188f5a87bd044`。三个输入、参考结果、验证标准及预算配置沿用首批版本。新提示对应一次诊断后复测，应单独记录。串行与双 worker 耗时比较使用 v2 的两次运行。

## v2 双 worker 重复实验

在相同三个任务和策略上各重复三次。两个分片分别提交 13 和 14 槽，同时最多执行两槽。合并覆盖 **27/27**，独立核对 **63 份产物**。总墙钟时间为 **206.148 秒**，共记录 **36 次模型调用、114,389 tokens**。未结预留、未知用量、策略拒绝、待人工核对和未完成槽位均为 0。

| 策略 | 完整交付 | 模型调用 | 已知 token | 单槽平均耗时 |
| --- | --- | --- | --- | --- |
| `hard-only` | 9/9 | 9 | 37,780 | 11.55 秒 |

## 真实 CPU、内存与日志压力

OpenSandbox 资源探针通过 **14/14**，耗时 **58.6 秒**，模型调用为 **0**，并确认删除沙箱。沙箱配置为 1 vCPU、512 MiB，分别用真实 CPU 负载、内存负载和高日志输出检查三种降档路径。

| 信号 | 降档 | 恢复 |
| --- | --- | --- |
| CPU | 连续两次约 99.6% 的 SDK 采样，后续派发上限由 2 降至 1 | 连续两次约 5.2% 的低值，恢复至 2 |
| 内存 | 连续两次约 345 MiB 的 SDK 采样，后续派发上限由 2 降至 1 | 连续两次约 26 MiB 的低值，恢复至 2 |
| 日志 | stdout、stderr 各保留 4 KiB。用截断后的合计字节下界触发降档 | 两次短日志采样后恢复至 2 |

CPU 和内存测试中的在途命令均正常完成。三种策略都在同一客户端进程内序列化并恢复状态，再注入遥测缺失，确认缺失样本不会解除降档。逐命令 CPU time 和 peak memory 仍标为未知。真实探针检查策略计算出的后续派发上限，调度器实际采用该上限由 60 项相关回归中的调度用例覆盖。
