## 历史实现与验证记录

Date: 2026-11-17. Status: **assembler, SQLite recovery and trusted opt-in production Harness role-request integration locally verified**; real-model long-task quality evaluation remains open.

Files: `src/context/assembler.ts`, `src/context/checkpoint.ts`, `src/context/harness-request.ts`, `src/adapters/harness/roles.ts`, `src/adapters/harness/composition.ts`, corresponding context tests and `tests/adapters/roles-context.test.ts`.

`assembleContext(entries, window)` separates system, task, visible plan, tool pair, history, summary, entities and artifact-index layers. The caller owns classification: model/tool data cannot choose a trusted system layer through a public input endpoint. Tool output is emitted only as a tool message; a tool call and its result are retained or dropped together.

Capacity equals model window minus output reserve and safety reserve. The caller provides a tokenizer over the fully translated request, including provider framing/tool schema overhead. The exported byte-based estimator is a deterministic demo estimate, not a provider guarantee. Task cumulative budget is deliberately absent from window arithmetic.

Mandatory entries, system/task constraints, artifact indexes and the configured most recent complete tool pairs remain intact. Exact duplicate older logs are removed before optional old tool/history/plan entries. If required information cannot fit, the result is `paused / REQUIRED_CONTEXT_TOO_LARGE`; callers must not dispatch its oversize messages. The assembler never silently truncates constraints to report success.

Validation: assembler tests — **9 passed**; SQLite checkpoint tests — **10 passed**. The final combined context/API command recorded in P3-05 passed 38 tests and `pnpm typecheck` passed. Assembly coverage includes capacity accounting, hostile tool text stays out of system, paired tool trimming, duplicate log removal, mandatory duplicate evidence, required-context overflow, deterministic immutable behavior, blank identities and malformed/non-object tool arguments, and invalid windows/counters.

Before/after example in tests: task + old 50-character tool result + recent result under a 20-token test capacity becomes task + recent complete call/result pair; the old pair is recorded as dropped. With protected context itself too large, no protected entry is removed and the request pauses.

`ContextCheckpointStore` persists entries, monotonic context version, fingerprints, summary state and coverage in the real SQLite component table, bound to run/session/budget scope/input hash/policy version. Save plus metadata event is transactional. Compare-and-swap rejects stale writers; hash/schema/binding checks reject corrupted or foreign snapshots. The hash detects accidental content changes; it does not authenticate against an actor able to rewrite the database and recompute the hash.

Recovery closes/reopens SQLite, verifies summary settlement receipts against the owning ledger and recomputes assembly for the current model window. A smaller window pauses without losing task constraints, artifact references or recent tool evidence. An update during asynchronous receipt verification is rejected. These are actual persistence/recovery component tests, not a production long-task process-restart run.

Production connection is opt-in through `createRuntimeHarnessIntegration(...).createRolePort(ctx, { provider, model, maxOutputTokens, context })`. The composition supplies the existing service store and budget. Trusted host configuration supplies `modelWindowTokens`, `safetyReserveTokens`, `countRequestTokens` and optional `initialEntries` / `summary`; no public tool can classify its own text as trusted system context. With context omitted, the original one-message role request remains compatible.

The shared run checkpoint automatically includes the stored mandatory task. Each request counts the complete translated DTO: fixed role system instructions, task, current input, selected context, tools and caller-defined provider framing; output/safety allowances are then reserved. The exact role DTO is counted again before stream dispatch. Optional history and summary become untrusted recall messages, while original tool-call/result IDs remain paired. A successful role adds its input/result and original receipt reference to durable history through version compare-and-swap; the same recorded call ID is not replayed.

Required-context overflow, unresolved summary and unknown accounting raise `RoleContextError` before the main role stream starts. It extends the trusted `RoleNotDispatchedError`, so the workflow can persist that the main role was not dispatched rather than misclassifying it as an unknown paid role call. The composition records a durable runtime context block and pauses. Resuming requires the trusted host's `validateContextResume` check; pending summary or unknown accounting still blocks a later request. Ordinary post-dispatch failures retain conservative pending/reconciliation semantics.

Final verification: **85 tests passed across 9 files**, including 11 role-context tests, all 5 opt-in real local Harness/budget cases, 5 runtime context-block cases and 17 serial-workflow cases; `pnpm typecheck` passed. P3-05 records the exact command. The role tests verify actual DTO trimming, fixed input/tool-schema accounting, hostile-summary placement, receipt separation, cross-child-role root-summary recovery, duplicate-call suppression, pending/unknown guards and composition pause handling.

No real-provider tokenizer correctness or long-task completion-rate gain is claimed. The supplied test counter is a controlled estimate including framing; deployments must supply a tokenizer appropriate to the actual provider and account for any downstream plugins that add request content.
