## Retry matrix

| Failure class | Automatic retry |
| --- | --- |
| `transient-unsent` | Controller permits within bounds; actual code executor permits only a persisted `FAILED / SANDBOX_CREATE_FAILED` attempt with null sandboxId, executionId and workDir |
| `transient-idempotent` | Controller permits within bounds; actual code executor does not classify a code execution into this category |
| `invalid-input`, `budget`, `cancelled`, `unknown`, `permanent` | Refused; correct, reconcile, or await explicit action first |

`begin` persists a dispatch intent and increments the attempt count before external side effects. Restart does not clear attempts or `nextAt`. The controller rejects a non-running/expired run, max-attempt exhaustion, active backoff, and every non-retryable last failure. Exponential delay is capped by the configured maximum.

The returned `attempts` value must be supplied as `failed(runId, key, attempt, kind)`. A late classification from an older attempt is rejected. Repeating the same outcome returns the existing state and does not append another event or extend backoff; a conflicting outcome requires explicit reconciliation. An unresolved pending dispatch cannot be retried. Duplicate reports recompute eligibility against the current task status and original deadline without moving the persisted retry timestamp.

Retry state is now version 2 with an explicit idle/pending/failed phase. Version 1 cannot distinguish a pending unknown dispatch from a classified unknown outcome, so it is refused rather than silently migrated or reset. Invalid persisted counters/phases and nonfinite, negative, fractional or overflowing timing bounds are refused. There is no automatic migration or reconciliation command in this module.

## Actual service composition

`DurableRetryExecutor` implements `RuntimeCodeExecutor` and calls the actual `RuntimeService.executeCode`. A host can pass it as the Harness tool executor or the serial/composition executor; its retry policy is trusted host configuration. Each accepted code retry creates a fresh persisted service attempt, using the same step/input hash and sequential `attemptNo`. The wrapper records input and code hashes, runtime configuration and retry-bounds fingerprint, runtime identity, root session, original scope and deadline before awaiting admission. Caller-provided input bytes are copied before any await.

`retry-executor` component state records the dispatch generation and expected service attempt number. A SQLite transaction claims the generation with `RetryController.begin`; a second executor/service object cannot claim an unresolved generation. The real attempt is correlated by step, input/code identity and expected attempt number. Different tools must not bypass this executor and independently dispatch the same step: the wrapper deliberately refuses historical attempts without its own binding.

Before each service invocation, the wrapper rechecks the root session's original scope, available global/work budget, complete usage, cancellation, run state and original deadline. Budget accounting remains owned by the budget port; the wrapper does not reserve, settle, refund or reset it. An admission failure consumes a wrapper dispatch intent but creates no service attempt and is never automatically retried. Consequently a blocked admission can have an expected next `attemptNo` without that attempt having been created.

Only the persisted unsent code condition above permits automatic retry. An exception's `retryable` hint is insufficient evidence. Sandbox creation can itself have an uncertain provisioning outcome; this rule proves no Python command was dispatched and does not claim exactly-once provisioning or automatic recovery of an unrecorded created sandbox. Rejected inputs, insufficient/unknown budget, cancellation, timeouts, and unresolved dispatches are blocked. A committed nonzero script exit is returned as its existing result rather than blindly retried.

Classified safe failures keep their original count and `nextAt` through reconstruction and actual SQLite close/reopen. Waiting rechecks cancellation/pause/deadline and the transaction rechecks the generation before dispatch. An interrupted local wait leaves classified state resumable; a pending intent without a committed service result is conservatively blocked, even if a later inspection finds an unsent attempt. This intentional crash-window restriction requires explicit reconciliation, not a fresh executor. No management command to clear a blocked/pending wrapper is supplied here.

Committed results, including the local service-commit/wrapper-commit window, replay the same attempt after artifact manifest/content verification. An unknown attempt which `RuntimeService.recover` explicitly reconciles and commits can likewise replay its original result. Replaying a result never creates a new service attempt or reexecutes remote code.
