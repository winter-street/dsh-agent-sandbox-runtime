## Parallel execution boundary

ParallelWorkflow accepts a fixed host maximum of 1–8 and reads `currentLimit` before each new launch. This hook can combine the budget policy with resource `maxNewConcurrency`. A smaller limit affects future dispatches; it never claims already-running commands were terminated. Zero returns a resumable graph snapshot with pending work when active work has drained. The host must invoke the graph again after the policy permits new work. The scheduler periodically rechecks root pause/cancel/deadline even when an execute callback hangs.

The graph-wide SQLite claim protects separate scheduler objects, not only a local busy flag. The trusted host identity and parallel/cancellation bounds are fingerprinted. Exceptions from policy/admission/execute/verification enter cleanup; a generic post-dispatch exception needs a confirmed stop before it can become a known failure. Explicit execution/usage uncertainty remains UNKNOWN. Cancellation uses an AbortSignal plus a separately bounded remote confirmation; abort alone never confirms a stop. A hanging/rejected/false cancellation callback returns within the configured bound and preserves UNKNOWN. Late completion callbacks are fenced from updating graph state. Outstanding raw execute/cancel promises retain the local owner until quiescent, preventing an overlapping host recovery.

Two recovery objects also require the persisted reconciliation claim before invoking remote recovery; a last-minute CAS alone is insufficient. A test with two distinct RuntimeBranchWorkflow objects blocks the first at fake inspect and verifies the second fails before a second inspect/collect/finalize. Cross-process writes remain guarded by RuntimeStore's existing writer lock.

## RuntimeBranchWorkflow

The concrete host-only composition instantiates a separate actual RuntimeService per branch. Each deterministic child has its own run/step/attempt slot, remote sandbox and physical artifact directory:

```text
<artifact-root>/runs/<childRunId>/attempts/<attemptId>/files/...
```

The merged `branches/<nodeId>/...` manifest is a virtual name with verified child run/attempt/artifact provenance; it does not pretend the files were copied into a second physical directory. The existing single-unresolved-attempt-per-run restriction is preserved. Child IDs, original parent input, fixed code/input hashes, expected artifacts, validator version and dependency hashes are durable. Historical creation/dispatch intents cannot automatically create a second attempt after restart.

Every child uses a pre-existing host-selected session in the same root budget scope. Scope lookup uses `create:false`; no allocation, reserve, settle or reset is invented by this fixed-code composition. The original deadline and policy are inherited. Admission explicitly refuses unknown usage or exhausted work budget, including when core policy is observe-only. External model requests use the original metered host adapter. The local tests below use fake remote ports. The real probe uses fixed Python branches and explicitly controlled usage against the original budget plugin.

Successful code execution is followed by expected-artifact checks and the child RuntimeService's independent validation/finalization. Results are accepted only from a SUCCEEDED child with the matching validation receipt. Wrong answers, missing output and nonzero exits cannot produce full completion. Verified dependency bytes become explicit child inputs. Parent graph completion does not finalize the parent task/report automatically.

Host reconciliation inspects the existing child; it does not call executeCode. A known completed remote execution may be collected, committed, resumed under the original scope/deadline and independently validated. An intent without durable execution identity stays UNKNOWN. Unconfirmed creation stays UNKNOWN as well. Confirmed cancellation reclaims the stopped child sandbox, including cancellation during a pending independent validator; a late validator cannot mark that child successful. Failed sandbox destruction is recorded as `sandbox.cleanup_required`, rather than silently claimed cleaned.

## Failures found and preserved

The first attempt failed during probe setup because read-only scope lookup preceded finalize allocation. The probe now opens the root scope through the original writable budget port before allocating. The failed report is retained at `.runtime/workflow-branches-real-20261119-194316-287a9b82/report.json`, with SHA-256 `51ba963edd86e06b18c21b8e2858dd9b61312c16999d4b0de8557dfee1e3d728`. It created zero sandboxes.

The next attempt reached actual branch creation and exposed a production compatibility defect. The generated child run ID is 71 characters, while OpenSandbox metadata labels allow at most 63. The adapter now preserves a legal short label as before and deterministically encodes a longer local identity as `run-` followed by a 59-character SHA-256 prefix. The full run ID remains in `SandboxRef`, runtime storage and execution directories. Repository searches found no runtime lookup or discovery filter consuming the remote `runId` label. Existing sandbox connections and recovery use the persisted sandbox ID.

That failure is retained at `.runtime/workflow-branches-real-20261119-194648-f2f27caa/report.json`, with SHA-256 `c70da48986731c107868fe08947437eff25b94cd65a1f725562c52ffcbb4035c`. Its shared-budget check passed and sandbox creation count stayed zero.

The targeted regression uses the same 71-character child ID shape. It checks the remote label limit and format, deterministic mapping, distinct labels for distinct full IDs, and preservation of the full local execution identity. The existing short-ID assertion still passes.
