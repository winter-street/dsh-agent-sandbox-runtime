## Delivered

- `src/resources/index.ts`: explicit known/unknown metrics with units, source, quality and deployment evidence. CPU utilization is a ratio, memory is bytes, command wall time is milliseconds. Cumulative per-command CPU time and peak RSS remain `not-supported`; the metrics endpoint does not establish them.
- `src/resources/policy.ts`: repeatable decisions with consecutive high/low samples, separate enter/recover thresholds, duplicate/stale sample detection, configuration fingerprint and serializable state. Unknown readings cannot clear an existing throttle. A lower-bound reading can establish high pressure but cannot establish recovery. Observe mode reports proposed concurrency; enforce mode applies a maximum for **new dispatches only**.
- `ResourcePolicyController` and `RuntimeBranchWorkflow` provide an opt-in composition seam: the trusted host supplies a sampler, the controller restores/saves state through `component_state`, and `ParallelWorkflow.currentLimit` applies the effective limit before each new branch launch. Existing branches are never interrupted by this soft policy.
- `OpenSandboxAdapter.sampleResources(ref, policy)`: optional SDK sampling, bounded local wait and at most one pending metrics request per execution. Collection attaches verified retained-log byte count, output byte count and file count. SDK resource sampling during collection is opt-in via `resourceSampling`.
- Optional `SandboxPort.sampleResources` and `CollectedExecution.resources` preserve existing adapter compatibility. Policy code is in `src/resources/policy.ts` rather than the originally proposed `src/policy/resource-rules.*` to keep normalization and the sampling policy together.

## Inspected upstream evidence

OpenSandbox source commit `4ae99691ff0a62594614df90a86ecbee07add966`; installed `@alibaba-group/opensandbox@1.2.1`.

- `sdks/sandbox/javascript/src/adapters/metricsAdapter.ts`: absent metric fields become zero through nullish defaults. Consequently this adapter cannot distinguish a measured zero from an omitted field; CPU/memory zero readings are explicitly `sdk-zero-ambiguous`, not evidence of idle/empty resource use.
- `sdks/sandbox/javascript/src/models/execd.ts` and `adapters/commandsAdapter.ts`: command start/finish timestamps are optional `Date` values. Confirmed duration is finish minus start. A running duration uses the remote metric timestamp as a lower bound; local network latency is never presented as execution duration.
- `components/execd/pkg/resources/resources_linux.go`: missing/unreadable cgroup data can fall back to host `/proc` counters. This API does not expose a per-sample scope flag. CPU/memory therefore need an operator-provided deployment evidence reference, matching CPU capacity and matching memory capacity before they are marked known. A profile is an explicit assertion backed by deployment acceptance; capacity matching alone is not proof of isolation.
- `sdks/sandbox/javascript/src/config/connection.ts`: `disableMetrics` disables SDK lifecycle telemetry, not the sandbox resource endpoint. Metrics SDK calls expose no request AbortSignal. A local deadline returns unknown; it does not claim the remote request was cancelled. Repeated polling reuses a still-pending request to avoid accumulating requests for one execution.

The runner's user-owned files are not a trusted CPU/RSS counter. No `resource.getrusage` result from a writable task directory was promoted to authoritative process accounting.

## Historical follow-up list before the real-pressure probe

Items 1–3 below describe the earlier evidence gap. The later reports cover the original task through the accepted deployment, real pressure and missing telemetry, durable state round trip and scheduler regressions. Broader deployment and process-termination studies remain possible extensions.

1. Wire a deployment-specific sampler and resource-policy profile into the production branch host. The optional branch scheduler bridge and SQLite persistence are tested, but the generic single-run execution limit remains one and has no lower parallelism to reduce.
2. The one-sample profile is tied to the bounded deployment evidence, but sustained verification is still required for the deployed execd/cgroup scope, CPU and memory quotas, timestamp alignment and supported resource fields.
3. Drive sustained CPU/memory pressure, a transient spike, missing metrics and restart on that deployment. Record real samples and scheduler decisions. Check that hard CPU/memory/TTL constraints are unchanged.
4. When using log pressure, its limit must account for both independently bounded stdout and stderr streams. Retained bytes are not a measurement of discarded output volume.
5. Chunking is not implemented by this module; it never invents a chunked alternative or snapshots a Python process. Resource samples remain per sandbox/command and must not be summed as per-branch memory if branches share a sandbox.

The original single-sample report alone did not close the real-pressure requirement. The current assessment incorporates the later reports.
