## Production boundary and configuration

The trusted host configures `createHarnessRolePort({ context: { entities: { index, query }, ... } })` (or the composition's corresponding `createRolePort`). Its query callback selects terms, types, limit and inputVersion for the current role; the run ID comes from the owning role request. Model JSON cannot choose a different run or make recall trusted system instructions. This is explicit opt-in; no entity extraction or model call is added when absent.

`retrieveEntityContext` uses `EntityIndex.queryVerified`, then emits optional `entities` context with original source IDs, versions, hashes and JSON Pointer fragments. The existing assembler counts the complete translated Harness request, including fixed role instructions, current input, tools, output allowance and safety reserve. Entity entries can be dropped as whole optional items; mandatory instructions keep their existing protection. Recall remains user/plugin evidence and never becomes system content.

Retrieval runs after optional historical compaction and is not persisted into the context checkpoint or summarized. When entity recall is enabled, role history records only completion identity and the original budget receipt, not the response/input's potentially entity-derived values. The serial workflow retains its full role results separately. The default context behavior without entity recall is unchanged. Independently supplied initial/history/task entries remain the trusted host's responsibility: enabling recall does not invalidate or repair arbitrary old facts the host already embedded in those entries.

A rejected retrieval occurs before the main role stream and is exposed as `RoleNotDispatchedError`, so a corrected host query can safely retry through the existing workflow boundary. This does not broaden replay of unknown or already dispatched model calls. Historical compaction, if explicitly enabled, still uses its own metered receipt before the role ledger cursor.

## Evidence rules

`createRuntimeEntityEvidence` supplies both metadata checks and asynchronous content verification:

| Source | Ownership/version | Integrity and locator |
| --- | --- | --- |
| Input | Trusted host callback keyed by run ID and input ID; exact document version | SHA256 of actual input bytes; strict UTF-8 JSON; JSON Pointer must resolve |
| Durable event | Event must belong to the requested run; version is its exact event sequence | SHA256 of canonical event payload JSON; pointer must resolve |
| Committed artifact | Artifact must appear in that run's durable committed records; version is attempt ID | Async `ArtifactStore.read` checks actual manifest/content bytes against SHA256; pointer must resolve |

Locators are URI-fragment JSON Pointers (`#`, `#/rows/7`); escape/percent decoding is checked, absent properties and invalid array indices are rejected. An artifact merely published on disk but not committed to runtime state is not eligible. The synchronous component `query` verifies metadata; production `queryVerified` requires a content verifier and reads real artifact bytes. Disk corruption after insertion removes that hit from production recall.

Stored facts have schema and fact-hash checks. Input-version changes advance a durable generation, including changing back to an earlier label. Retrieval checks the version/generation again after asynchronous content reads and checks that selected records have not changed. A stale query or invalid stored fact is rejected, and a source with a stale/bad hash is excluded. Runs remain separate even if they share a root budget.

The runtime evidence adapter currently supports deterministic facts. It does not supply model-extraction receipt verification, so model extraction is rejected by default. The component extension point requires a verified owning-budget settlement for model-extracted facts; this work did not add a model extractor. The fixture copies a known JSON row deterministically. Hash/pointer verification proves source ownership, location and integrity, not the semantic correctness of arbitrary extracted attributes or protection against an attacker who can rewrite the entire database and its hashes.

## Actual Harness and original budget integration

`tests/context/harness-entities.test.ts` installs actual Cordis, Harness LlmRuntime/session/system/tool/agent services, and the locally built original budget plugin. It drives the actual `createHarnessRolePort` stream with a deterministic provider, SQLite, real input bytes and the real artifact store adapter. It executes no Python, paid external model or real sandbox.

The scenario checks the actual dispatched DTO against the complete request counter, source hash/locator presence, preserved mandatory task/system content and untrusted recall placement. It closes/reopens SQLite, reconstructs the index/evidence binding and recalls the same fact. It checks cross-run isolation, rejects a stale host query without provider dispatch, hides source bytes after corruption, clears previous facts after input changes, prevents generation resurrection when a version label returns, and drops entity recall under a smaller window while preserving mandatory task instructions. Six provider calls create exactly six original-ledger reservations and six settlements in one unchanged root scope; synthetic usage is 6 × (20 input + 2 cache-read + 8 output) = 180, reserved=0 and unknown=0. Retrieval adds no provider call or independent budget debit.

The companion six evidence tests resolve actual input and event content; require artifact commit; detect corruption of an artifact's real file; reopen SQLite; reject cross-run/wrong-version/bad-pointer/bad-hash input, stored fact mutation, absent content-verifier support and an input-generation change during async verification. Four original component tests remain passing.

## Fixed controlled comparison

The integration freezes 60 JSON rows and one expected target (`device-7`, Charger Seven, alerts=3). Both configurations use the same mandatory task, current input, deterministic full-DTO counter and 1,200-token window with 128 output and 20 safety tokens. The whole raw historical document does not fit and is dropped. The indexed variant can retain one verified fact:

| Metric | Without index | With index |
| --- | ---: | ---: |
| Full original source bytes | 16,674 | 16,674 |
| Recalled fact JSON bytes | 0 | 307 |
| Expected target present in dispatched context | 0/1 | 1/1 |
| Retained final provider DTO bytes | 403 | 810 |
| Controlled estimated input tokens | 199 | 334 |
| Synthetic reported usage per provider call | 30 | 30 |

The indexed request is larger than the trimmed baseline because it retains the evidence the baseline lost. The smaller recalled representation is not a measured token/cost saving against that baseline. One target's context presence is not task correctness, and fixed provider responses do not establish answer accuracy, retrieval quality at scale, real tokenizer usage or billing savings. The test prints this exact comparison as JSON for reproduction; Broader retrieval accuracy and real-model cost studies are optional follow-up measurements.
