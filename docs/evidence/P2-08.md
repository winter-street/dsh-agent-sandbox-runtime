# P2-08 — Deterministic budget policy decisions

Date: 2026-11-16. Status: **pure policy module implemented and verified**. P2-10 production scheduling/request enforcement is separate integration work. P2-11's serializable state and replay rules are implemented here; its database/checkpoint transaction integration is not established by these tests.

Files: `src/policy/engine.ts`, `tests/policy/engine.test.ts`. Runtime baseline `dff1a01`; implementation commit is assigned by the coordinating task. Node `22.22.2`, pnpm `11.7.0`, TypeScript `5.9.3`, Vitest `4.0.18`.

## Integration contract

```ts
const engine = new PolicyEngine(config.policy);
const decision = engine.evaluate(snapshot, action, previousState);
```

`snapshot` includes the budget service's `BudgetSnapshot`, cancellation/deadline/permission flags, actual inflight model count, and monotonically increasing step/settlement boundary counters. `action` describes model/tool/agent creation or maintenance. The composition root supplies these values; they are not model-controlled permission or budget arguments.

The decision returns `allowed`, `disposition` (`allow`, `wait`, `deny`, `finalize`), stage, all reasons, applied/proposed limits, separate used/reserved/combined pressure, notifications, and the next JSON-serializable state. The function performs no I/O, hidden clock reads or mutations of its inputs.

The caller must atomically persist relevant runtime state, policy state, notifications and event cursor. The policy never writes or duplicates the authoritative budget ledger. An allowed decision is a preliminary check: the budget plugin still makes the final atomic reservation. If `requiresReestimate` is true, apply the output cap and recompute the complete request before re-evaluating/reserving. Conservative estimates can reject otherwise smaller requests until that recomputation; do not treat this pure helper as an exact provider token counter.

## Implemented rules

- Thresholds use **used plus reserved / total** at 50%, 65%, 80%, 95%; they are configurable initial values, not measured optimal settings.
- Conserve reduces subsequent model concurrency to one and disables optional work. Focus additionally blocks new agents. Only prose output can be shortened; code and structured output retain their supplied cap, and prose retains its minimum effective output.
- Cancellation, permission denial, elapsed deadline, unknown usage, original concurrency ceiling, total budget and class budget remain effective in observe mode. Maintenance may collect/checkpoint/clean up after cancellation or unknown usage, but cannot bypass its own permission denial.
- Observe returns baseline applied limits plus the proposed soft decisions. Enforce applies the soft limits; the helper cannot cancel or truncate an already-running call.
- Pressure caused only by inflight reservations waits for settlement without irreversibly latching finalize. Required ordinary calls that no longer fit can enter finalize; oversized optional requests cannot force that transition.
- Finalize model requests require trusted final-report intent, a latched finalize stage and sufficient total/class allowance. Zero finalize credit therefore requires the caller's non-model template fallback.
- Stage notification keys survive JSON serialization and are not repeated on re-entry. Downgrading pressure requires hysteresis, at least one settlement and the configured step-boundary cooldown (default two).
- Finalize remains latched across restart. `releaseFinalize(state, reason)` is an explicit host/operator action; the caller must audit it. Releasing does not change any budget balance.
- State restore validates schema, rule version, config fingerprint, latch consistency and monotonic counters. Mode/config changes require explicit migration; they never silently reset notification history or scope.
