# P2-09 — bounded finalization and automatic template fallback

2026-11-19 复核。收尾分类额度、一次计量、未知用量及模板回退已完成原要求验收。默认应用已接入 FinalizationCoordinator，真实 demo 的 work/finalize 分别为 3908/66 tokens，三份产物独立验证通过。 证据汇总见 [QA-03](QA-03.md)，G1 前置见 [QA-02](QA-02.md)。

以下保留早期实现与验证记录，当前验收采用本段及 QA-03 的逐项结论。

Date: 2026-11-17. Status: coordinator and controlled integration implemented/tested; external provider acceptance and default application integration remain open. Runtime baseline commit `dff1a01`; changes are in the shared working tree. Original budget implementation commit `b640a3a15daf520c78c61303200bca23a601d9ea`.

Implementation: `src/core/finalize.ts`, existing `RuntimeService.finalize`, `PolicyEngine`, Harness model-policy/composition, original budget work/finalize allocation. Tests: `tests/core/finalize.test.ts` and `tests/scenarios/budget-runtime.test.ts`.

`FinalizationCoordinator` accepts an optional trusted `FinalReportPort`, copies/freezes the complete model request and estimates messages/system plus output using the same documented byte heuristic as the original budget hook. Finalize credit zero, or insufficient remaining global/class credit, selects the deterministic template without dispatch. It never allocates credit, reserves or settles model calls. Paused/expired runs cannot start a report model call. The template explicitly distinguishes partial delivery and pending required checks.

For an affordable optional enhancement, the host port must consume one original-plugin automatic finalize call against the original root session. The coordinator accepts prose only after new ledger receipts contain exactly one matching reserve/dispatch/settle sequence for the correct scope, session, purpose, provider, model and estimate. Missing/wrong-purpose accounting proof fails closed to partial delivery. Model prose is a separate optional field; `RuntimeService.finalize` still verifies artifacts, unresolved attempts and registered independent required acceptance before success. Failed validation cannot be overwritten by an optimistic report.

The prepared request is checked at runtime before JSON copying: only `provider`, `model`, `sessionId`, `messages`, `system` and `maxTokens` are accepted. Extra fields such as empty `tools`, `toolChoice`, retry controls, `signal`, purpose overrides and even unsupported fields whose value is `undefined` are rejected before any report intent or model dispatch. Provider/model/session and text request shape are checked; the frozen request that is estimated is the exact payload handed to the trusted port. The port must still enforce its documented one-call/no-retry contract; this is not a sandbox for arbitrary adapter code.

Receipt verification requires a nonempty original `modelCallId`, bound reserve session/scope, exactly one reserve/dispatch/settle sequence, increasing post-snapshot cursors, distinct event IDs, consistent envelope/payload scope and valid usage buckets. The original plugin's `foldReservationEvent` binds dispatch and settlement to the immutable reservation subject by `reservationId`, rejecting unknown reservations and conflicting call identities; those tail events normally do not repeat session/modelCallId. If a port supplies such metadata, conflicting values are rejected. This proof relies on the trusted original ledger and host port, not on matching provider prose or independently attesting the provider payload.

A persisted report intent prevents silent model resending after reconstruction. Unknown usage, an interrupted call, or a persisted unverified attempt produces explicit partial delivery, preserving the original reservation. No retry, credit refund or second ledger is introduced. An unverified accounting proof can conservatively prevent full success even if the model returned text.

Concurrency is bounded by the existing single-writer RuntimeStore lock, a shared per-store coordinator guard and a synchronous SQLite transaction that checks/claims the durable report intent. Separate coordinators sharing the store cannot dispatch twice; a new writer cannot open the same active store directory. This is a single-writer guarantee, not distributed locking. Run status and revision are checked after awaited admission reads, inside intent creation and before committing to service finalization. Cancel, failure, pause or even pause-and-resume during model generation therefore prevents stale completion; any actual late model usage remains accounted. Cancellation does not by itself promise transport-level abort of an already dispatched provider call.

Coverage includes finalize=0, large **input** with small output exceeding finalize credit, one metered enhancement, wrong/missing/corrupted receipt proof, unsupported runtime request fields, required validation failure, unknown before/during report generation, concurrent coordinators, persisted dispatch intent, state changes during model await and cancellation during an asynchronous admission read. Controlled integration uses actual Cordis/DSH hooks and the patched original plugin: an affordable report settles 15 synthetic tokens into finalize once; interruption retains unknown. Model and sandbox outputs in these scenarios are controlled fixtures, not external inference or billing evidence.

Validation commands and exact totals are recorded in [P2-12](P2-12.md). The source coordinator is callable and exercised directly in scenarios; a complete application bootstrap/profile with optional report generation is not delivered by this change. There is no external provider credential in the process environment, no provider-native SSE validation, no price table and no invoice reconciliation. Full charging-analysis/G2 acceptance remains open.
