### Behavior

The summarizer deduplicates first, then checks a configurable window-pressure trigger (default 70%). It summarizes only optional old history, tool pairs and visible plans. Required constraints, artifact indexes and recent tool results stay outside the summary. Each replacement records covered IDs/revisions, original source references, a content fingerprint, token counts and the actual settlement receipt.

The complete summary request includes system text, source history and output allowance. It must fit both the model window and the existing root work allocation. No-budget/unknown-usage paths use deterministic trimming. Defaults allow one attempt per source fingerprint and three total attempts; failure or no reduction consumes an attempt. State is serializable and is durably saved as pending before dispatch. A recovered pending attempt is not auto-retried. Replacement context, provenance and final state go through one caller-provided atomic commit; a commit failure does not return successful compaction.

`createHarnessSummaryPort` calls actual `ctx.llm.stream` with `purpose: compaction` inside `budget.withPurpose(session, work, async () => consumeEntireStream())`. The original budget plugin owns the reservation and settlement; this adapter never debits a second time. It correlates a unique same-session reservation after the initial ledger cursor to its settlement event. Ambiguous same-session concurrency is conservatively rejected for summary attribution; the completed call's real usage remains in the budget ledger.

### Observed metering evidence

- Real rc.6 Harness LlmRuntime + actual upgraded budget plugin + local controlled provider: one summary emits exactly one reserve and one settle event. Synthetic usage is 20 input + 2 cache-read + 8 output = 30, entirely in work allocation; finalize stays at zero, reserved returns to zero.
- No-usage finish: summary fails, one unknown call and its reservation remain; the next request is rejected before the provider is invoked again.
- Actual Harness + actual budget plugin + SQLite checkpoint: summary and coverage are persisted atomically, the database is closed/reopened and receipt verification succeeds against the real plugin ledger. Controlled provider usage remains exactly 30; available work allocation decreases once, reserved returns to zero and the provider is invoked once.
- Core tests also verify budget/window preflight, durable pending-before-send, failed/no-benefit retry limits over JSON restore, total attempt cap despite changed input, provenance, required-context preservation, binding mismatch and commit failure.

`ContextCheckpointStore.summaryPersistence` supplies the actual SQLite implementation. It records pending state before dispatch and commits replacement entries, coverage and final state with the metadata event in one transaction. It checks the active source fingerprint, exact coverage/source references, before/after token counts, protected constraints and unique reservation receipt. Receipt verification binds usage to the original scope and session without making new ledger debits. A stale writer, forged usage, wrong session/scope/reservation, concurrent asynchronous restore update or event publication failure is rejected. A pending attempt blocks replacement and further summaries even when source input changes. State parsing rejects inconsistent aggregate attempt counts and multiple pending attempts.

### Production role integration and final regression

Trusted host configuration can now enable compaction on actual Planner/Executor/Reviewer role requests. Summary and checkpoint restore complete before the role adapter captures its ledger cursor, preventing a summary settlement from being accepted as the main role receipt. Compaction always uses the original root session's work allocation, including when the current role uses a child session. The resulting shared coverage is therefore verifiable by subsequent child-role calls after reopening SQLite. Role correlation is returned separately from model JSON using the actual ledger reservation's modelCallId.

`harnessSummaryRequest` is shared by token counting and dispatch, so compaction admission includes its complete Harness system/message DTO and provider framing. The role path blocks unresolved summaries even when the configured window becomes larger, and unknown accounting blocks both work and further inference. A known-settled summary whose context commit was interrupted stays pending and needs reconciliation; the production adapter does not automatically buy another summary.
