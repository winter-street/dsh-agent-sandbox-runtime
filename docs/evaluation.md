## 三条部分完成的原因

| 任务 / 策略 / 重复 | 输入错误 | 已结算 token | 失败的必需步骤 |
| --- | --- | --- | --- |
| e08 / hard-only / 1 | MISSING_COLUMN | 31704 | 5 |
| e10 / tiered / 1 | INVALID_TIMESTAMP | 31727 | 4 |
| e11 / hard-only / 1 | INVALID_ID | 29767 | 5 |

三条的第一次 Python 执行均写出正确的错误 JSON，随后却断言 `report.md` 存在，产生 `AssertionError: report.md` 和退出码 1。错误输入按任务契约仅需错误 JSON；模型增加了不适用的自检。后续多次重复同类断言；e08/e11 还尝试从新调用的独立输出目录读取旧文件，产生 `FileNotFoundError`。

工具完成边界的提前验收只在成功且有产物的执行后触发；这些非零退出没有触发正常结轮。随后模型准入事件记录了 `GLOBAL_BUDGET_UNAVAILABLE` 和 `WORK_BUDGET_UNAVAILABLE`。e08、e10、e11 分别已结算 31704、31727、29767 tokens，对应已核对的账本余量为 18296、18273、20233，三次请求的输出上限均为 8192。三次拒绝都发生在预算预留前，原始 trace 和账本缺少被拒请求的完整估算及准入快照，无法独立重算拒绝条件。最终产物独立验证通过，但失败必需步骤仍存在，宿主以 `CONFLICT` 保留部分完成状态，未假报成功。逐条 trace、原账本、失败摘要及产物均保留在对应 `.runtime/evaluation-evidence/<runId>/`。

## 报告字段

原 `finalEvaluationEligible` 实现同时要求数据完整与 **所有任务完整成功**；原文档只把它解释成格式/覆盖条件，解释不完整。本轮未放宽这一门槛，也没有修改原始结果。

新增 `evaluationDataComplete` 表示真实 evaluation、冻结 suite、全部计划槽、完整 usage/耗时、已知统计及必需检查结果。检查为 false 是已知失败，与未检查的 null 分开。该字段只验证记录字段，仍须核对证据文件。

本轮扩充报告为：

```json
{
  "evaluationDataComplete": true,
  "acceptance": { "passedRuns": 177, "notAcceptedRuns": 3, "allRunsAccepted": false },
  "finalEvaluationEligible": false,
  "eligibilityBlockers": [{ "code": "RUN_NOT_ACCEPTED", "count": 3 }]
}
```

实际 JSON 还包括失败 runId 与明细。失败样本是可分析的实验结果；无需为使一个字段变成 true 重跑整个批次。新增三项报告回归后，`pnpm check` 通过：604 项通过、12 项跳过，类型、构建及固定输入验证通过。执行代码和配置指纹保持与本轮记录一致；只扩充离线报告和文档。

## 能够支持的结论与限制

本轮支持“完成 180 次真实模型与沙箱执行，独立验证所有交付产物，并识别出 3 次错误输入处理中的收尾失败”。它不能证明预算策略造成某个百分比的成本改善：顺序运行、每任务仅三次、生成随机性和三次修复循环都会影响总量。token 也不是货币成本，当前未做价格/缓存折扣与账单核对。

多数任务一次工具执行即完成，本轮不足以系统验证持续预算压力、资源压力、多 Agent 长任务或跨模型效果；同一任务三次重复也不是 60 个相互独立的任务。未报告统计显著性。完整演示入口已补齐并通过一次真实演示，干净源目录复现已通过；专项恢复、故障和资源压力的证据范围另见 [交付复核](evidence/N06-delivery.md)。
